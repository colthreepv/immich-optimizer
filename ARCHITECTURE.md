# Architecture

The original-first deployment has one server and one or more HTTP pull workers. The initial deployment targets one Immich owner and one server. A worker can run on the same host or on another host that can reach the server's worker API.

1. The server receives a client upload, stages eligible source bytes in its durable queue, and sends the original to Immich. It returns success only after Immich supplies an asset ID. If recording that ID fails, the server logs deferred optimization and can reconcile the intent later. A failed or uncertain upload is not acknowledged as a successful new asset.
2. A worker claims a queued job over the internal API, downloads the staged original, checks its size and hashes, and runs the JPEG-to-AVIF converter. It returns the result to the server. Leases and heartbeats track work in progress.
3. When replacement is enabled, the server's publisher uploads the result as a new Immich asset with a new ID. Immich's API does not replace an existing asset's bytes in place. The publisher verifies the result, migrates and verifies supported metadata and relationships, and persists the source SHA-1 alias. It then requests a fresh Immich sync update for the replacement and records that step before retiring the original. Unsupported or uncertain relationships hold the job for review.

The queue records source SHA-1 and SHA-256 hashes and the original asset ID. For a verified replacement, the source SHA-1 alias maps the original bytes to the replacement asset ID. This mapping supports duplicate checks and the experimental mobile checksum view. Existing verified aliases must remain available; enabling this pipeline is not a bulk import of existing assets.

Original retirement defaults to disabled. While `IUO_RETIRE_ORIGINAL` is false, worker claims are paused and source intents remain queued. Setting it to `true` permits processing and retirement for eligible jobs; held jobs require separate review and resumption. A synthetic fixture on Immich 3.3.5 has verified publication, supported relationships, checksum sync and spool cleanup. Trashing an original does not immediately reclaim its storage; Immich retains trashed assets until they are deleted permanently or expire.

The queue uses a single-writer, atomically replaced JSON snapshot and a spool on a local durable filesystem. It is not SQLite. Before releasing terminal job bytes, cleanup checks the active original in Immich for skipped or failed jobs, or the verified replacement for completed jobs. Held jobs retain their bytes for review. The defaults of 10,000 historical jobs and 100 GiB of spool data are admission limits. Cleanup frees spool space but does not remove historical job records. When admission fails, the proxy logs missed optimization and attempts a normal original upload to Immich.

The mobile checksum view is experimental. The initial phone gate is a read-only check of settings and sync behavior; retirement stays disabled while validation is pending. Before enabling retirement, turn off Sync Remote Deletions on every phone. In Immich Android 3.3.4, the setting is under Advanced. The server does not enforce it. Validate upload, sync, and deletion behavior with the actual mobile client before relying on it to remove local originals. A successful upload response alone does not establish that mobile deletion is safe.
